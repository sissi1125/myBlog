从前端转向更完整的服务端学习后，我发现后端知识很容易被拆成一串名词：Controller、事务、连接池、事件循环、SSE、Docker……单独看都能理解，放到一起却不一定知道它们为什么存在。

对我最有效的方法，是跟着一次请求走完整条链路。

## 一次请求经历了什么

一个浏览器发起 API 请求后，常见的路径大致是：

```text
浏览器
-> DNS / CDN
-> 反向代理或 API Gateway
-> 应用服务器
-> Controller / Route
-> Service
-> Repository / Database Client
-> PostgreSQL、Redis 或外部服务
-> 返回响应
```

这条路径不是每个项目都必须完整拥有。小型应用可以只有一个服务和一个数据库；只有当流量、团队协作或可靠性要求增长时，才需要逐层增加组件。

### 路由和 Controller：确定请求去哪里

路由负责把 `GET /users/:id` 这样的请求映射到处理函数。Controller 读取路径参数、查询参数和请求体，完成输入校验，再调用业务层。

它不应该承载大量业务规则。否则 HTTP 协议细节、领域逻辑和数据库操作混在一起，测试和复用都会越来越困难。

### Service：表达业务规则

Service 负责回答“这件事能不能做、应该按什么顺序做”。例如创建订单时，它可能需要检查库存、计算价格、写入订单，再触发后续任务。

把业务规则放在这一层，可以让同一套逻辑被 HTTP 接口、定时任务或消息队列消费者复用。

### Repository 和数据库：保存可靠状态

数据库访问层负责执行 SQL 或调用 ORM。PostgreSQL 事务保证一组相关操作要么一起成功，要么一起失败，但前提是这些操作使用同一条数据库连接。

这也是连接池存在的重要原因：

- 每个请求都重新建立 TCP 连接和数据库认证，成本很高。
- 所有请求共用唯一连接，又会让查询互相排队。
- 连接池维护有限数量的可复用连接，在并发能力和资源上限之间取得平衡。

连接池并不是越大越好。池中的连接最终都会消耗数据库资源，需要结合应用实例数、查询耗时和 PostgreSQL 的连接上限来设置。

## 进程、线程和协程分别解决什么

理解服务端并发时，我先把三个层次分开：

- **进程**拥有相对独立的内存和系统资源，是故障隔离与多核部署的重要边界。
- **线程**共享进程内存，由操作系统调度，适合执行可能阻塞的工作，但共享状态需要同步控制。
- **协程**是运行时管理的轻量任务。它在等待网络或磁盘 I/O 时主动让出执行权，让一个线程可以同时管理许多等待中的请求。

Node.js 的 JavaScript 业务代码通常运行在事件循环线程上。网络 I/O 主要由操作系统的异步机制处理，部分文件、DNS 和加密任务会使用 libuv 线程池。它很适合大量 I/O 等待，但 CPU 密集计算会阻塞事件循环，需要交给 Worker Thread、独立进程或专门的计算服务。

Python 的 `asyncio` 也通过事件循环管理协程，但异步链路需要使用支持异步的库并正确 `await`。对于 CPU 密集任务，通常考虑多进程、原生扩展或外部任务系统，而不是单纯增加协程数量。

所以，选择并发方式前应该先判断瓶颈：任务是在等待 I/O，还是正在持续占用 CPU？

## SSE、WebSocket 和普通 HTTP

普通 HTTP 适合一次请求对应一次响应。任务耗时较长或需要持续更新时，还可以选择：

- **轮询**：实现简单，但会产生重复请求，实时性取决于轮询间隔。
- **SSE**：基于 HTTP，由服务端持续向浏览器推送文本事件，浏览器支持自动重连，适合 AI 流式输出、任务进度等单向更新。
- **WebSocket**：建立双向长连接，适合聊天、协同编辑或需要客户端与服务端高频互发消息的场景。

技术选择不应该只看“是否实时”。还要考虑连接数量、断线恢复、消息顺序、鉴权，以及代理层是否支持长连接。

## 部署之后，后端才真正开始运行

代码能在本地返回结果，只说明功能链路成立。进入部署环境后，还要面对配置、资源和故障：

- 用环境变量管理配置，不把密钥写进代码。
- 用 Docker 固定运行环境，但把数据库等持久数据放在 Volume 中。
- 设置超时、重试上限和取消机制，避免请求无限占用资源。
- 记录结构化日志，并观察延迟、错误率、连接池和资源使用情况。
- 提供健康检查，让部署平台知道服务是否真的可用。

后端不是某个框架，也不是一组 API。它更像是一套约束：在有限的 CPU、内存、连接和时间里，让请求得到正确、可观察、可以恢复的处理结果。
