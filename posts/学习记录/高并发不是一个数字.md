刚开始学习高并发时，我看到的是一张很长的技术清单：CDN、负载均衡、Redis、消息队列、读写分离、分库分表。它们都可能有用，但“把组件全部加上”并不等于系统就能承受高并发。

高并发首先是一个测量和取舍问题。

## 先说明在测量什么

“系统支持一万并发”这句话信息不足。一万可能指同时保持的连接数，也可能指每秒请求数；请求是读取一个缓存值，还是执行一次复杂查询，成本完全不同。

至少需要同时观察这些指标：

- **并发连接数**：同一时刻保持了多少连接。
- **RPS / QPS**：每秒处理多少请求或查询。
- **延迟**：不能只看平均值，还要看 P95、P99 等尾延迟。
- **吞吐量**：单位时间处理了多少数据或任务。
- **错误率**：超时、限流、服务错误分别占多少。
- **饱和度**：CPU、内存、数据库连接、队列积压等资源距离上限还有多远。

只有给出请求类型、数据规模、机器配置和延迟目标，容量数字才有意义。

## 从请求链路逐层寻找瓶颈

### 边缘与入口层

CDN 可以就近返回静态资源，减少回源流量。反向代理或 API Gateway 负责 TLS、路由、鉴权和限流，负载均衡则把请求分发给多个应用实例。

入口层的关键不是“挡住所有流量”，而是尽早区分哪些请求可以缓存、哪些请求应该拒绝、哪些请求可以继续进入核心服务。

### 应用服务层

应用实例要尽量保持无状态，用户会话和任务状态放进共享存储，才能比较容易地水平扩容。

但增加实例之前，必须确认瓶颈不在下游。十个应用实例同时访问一台已经饱和的数据库，只会更快耗尽连接。

对 Node.js 或 Python 异步服务来说，还要特别警惕事件循环阻塞：同步文件操作、重度计算、过大的 JSON 解析，都可能让其他请求无法及时获得执行机会。

### 缓存层

Redis 适合保存读多写少、允许一定更新延迟的热点数据。缓存能减少数据库压力，但也引入了一致性和失效问题：

- 热点 key 同时过期，可能造成缓存击穿。
- 大量请求查询不存在的数据，可能形成缓存穿透。
- 大面积 key 同时失效，可能造成缓存雪崩。
- 更新数据库后忘记处理缓存，会返回旧数据。

所以缓存需要失效策略、随机过期时间、热点保护和可观测性，而不是简单地在查询前加一次 `GET`。

### 消息队列与任务系统

对于耗时较长、可以异步处理的写任务，消息队列可以削峰：入口先记录任务并快速返回，Worker 再按自身能力消费。

队列并没有消灭压力，只是把瞬时压力转换成积压。因此还要设计：

- 消费并发和速率上限。
- 重试次数与退避策略。
- 幂等键，避免消息重复执行产生重复结果。
- 死信队列和人工恢复入口。
- 队列长度、等待时间和失败率告警。

如果生产速度长期高于消费速度，最终还是会耗尽存储或让用户等待过久。

### 数据库层

数据库通常是最需要保护的一层。常见手段包括索引优化、批量操作、连接池、缩短事务、读副本和分区。

分库分表应该是较晚的选择，因为它会把跨分片查询、事务、一致性和运维复杂度带进系统。在此之前，通常应该先确认 SQL、索引、数据模型和访问模式是否合理。

## 背压比无限扩容更重要

系统不可能无限处理请求。可靠系统需要在接近容量上限时主动变慢或拒绝部分工作，而不是让所有请求一起超时。

常见的保护措施包括：

- 限流，控制单位时间进入系统的请求数。
- 超时，避免一个下游调用无限占用连接。
- 有上限的重试，并加入退避和随机抖动，避免重试风暴。
- 熔断，在依赖持续失败时暂时停止调用。
- 降级，优先保留核心能力。
- 有界队列，明确系统最多接受多少等待中的任务。

这些机制共同回答一个问题：系统过载时，失败是否仍然可控？

## AI 服务中的高并发更像资源调度

AI 应用经常调用响应慢、费用高且存在配额的模型服务。它的瓶颈不一定是本地 CPU，而可能是上游并发限制、Token 吞吐量、长连接数量和任务成本。

一个更实际的处理链路可能是：

```text
请求进入
-> 鉴权与限流
-> 幂等检查
-> 短任务直接执行，长任务进入队列
-> Worker 按模型和租户配额调度
-> 通过 SSE 返回进度或流式结果
-> 记录耗时、Token、错误类型和最终状态
```

还要允许用户取消任务。取消不仅是前端隐藏加载状态，后端也应尽可能停止排队、模型调用和后续处理，释放资源并避免继续计费。

## 我现在理解的演进顺序

高并发方案应该跟着证据逐步演进：

1. 定义容量和延迟目标，建立压测基线。
2. 优化单实例中的慢查询、阻塞操作和连接使用。
3. 对明确的热点增加缓存，对长任务增加异步处理。
4. 做好限流、超时、熔断和可观测性。
5. 再根据瓶颈水平扩容、拆分服务或调整数据架构。

真正的高并发能力，不是架构图上出现了多少组件，而是知道压力在哪里、系统的上限在哪里，以及达到上限时会发生什么。
